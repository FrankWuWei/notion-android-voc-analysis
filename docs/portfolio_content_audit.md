# Notion Android VOC 作品集內容審驗

## 專案真正要代表的能力

這不是一份 Notion 問題排行榜，也不是用 LLM 產生產品結論的展示。作品集要證明的是：能把大量公開評論整理成可重跑、可驗證、可回到原始來源的分析產物，並清楚區分資料訊號、待驗證假設與不能直接推論的事項。

面試官應在首頁快速看懂三件事：

1. 輸入是 6,186 則清洗後的 Notion Android 公開評論。
2. 產出是 159 個驗證後主題與 652 筆可回查證據。
3. 模型輸出經過程式檢查、修復或淘汰，而不是直接當成結論。

## Taste Review Gate

| 檢查項目 | 決策 |
| --- | --- |
| Subject | 從公開評論到可稽核產品議題的分析流程，不是一般 dashboard。 |
| Audience | 資料分析與 AI 應用職缺的面試官，需要判斷資料處理、模型使用、驗證與溝通能力。 |
| Single job | 首屏回答「處理了什麼、產出了什麼、為什麼可信」。 |
| Tokens | 深炭色為主；青綠標示資料與證據；珊瑚標示修正、限制與警示；沿用編輯式字級與窄圓角。 |
| Layout concept | 分析稽核紀錄：先交付與品質，再示範案例，最後說明方法與邊界。 |
| Signature element | 首頁的成果帳本，以明確單位呈現評論、主題與證據，不用漏斗或抽象標語。 |
| Generic-default critique | 每一段必須說明資料、產出或判斷邊界；刪除可套用到任何 AI 專案的口號。 |
| UI copy | 使用「時間切點前／後」、「固定期間追蹤案例」與「待驗證問題」，避免暗示更新造成改善。 |

## 現行內容審驗與處置

| 現行位置或語句 | 問題 | 處置 |
| --- | --- | --- |
| 首頁「不是用模型代替產品判斷……」 | 抽象、重複「可回查」，沒有說明實際交付。 | 改成具體數字與專案能力：評論、主題、證據及模型輸出驗證。 |
| 首頁只放資料範圍 | 只能看出資料量，無法看出專案成果。 | 保留資料期間與範圍，新增 159 個主題與 652 筆證據。 |
| 「三個代表性產品訊號」排在品質之前 | 樣本只有 6 筆，容易被誤讀成主要發現或問題排行。 | 改名「三個固定期間追蹤案例」，移到專案產出與品質之後。 |
| 「更新前／更新後」 | 即使有免責文字，仍會在視覺上暗示產品更新與 Android 問題有關。 | 全面改為「時間切點前／後」，並標示切點不是 Android 修復紀錄。 |
| 「更新後未觀察到相同詞組」 | 沒說明是規則命中，也容易被解讀為問題消失。 | 改為「切點後 28 天未命中相同規則」。 |
| 待驗證建議以產品動作開頭 | 看起來像已確定解法，與少量證據不相稱。 | 改成待回答的問題、為何值得查、如何驗證。 |
| 「35 + 4」 | 相加的是不同單位，讀者無法立即理解。 | 分別顯示「35 段引文、4 筆星等」。 |
| 品質流程使用連續步驟 | 批次、主題、證據與錯誤是不同單位，仍可能被當成轉換流程。 | 改為成果帳本與修復紀錄，不使用轉換式視覺。 |
| 方法區重複大量結果數字 | 與成果區重複，降低閱讀效率。 | 方法只交代目的、選擇、產出與檢查，數字以動態資料帶入。 |
| 限制未提公開評論代表性 | 容易讓讀者把評論頻率當成所有使用者的發生率。 | 明示公開評論不能代表全部使用者，也不能直接決定產品優先級。 |

## 新的閱讀順序

1. 專題概覽：資料、產出與專案能力。
2. 分析產出與品質：結構化結果、可回查證據、修復與淘汰紀錄。
3. 固定期間追蹤案例：示範如何從訊號進入驗證，不當成排行或因果分析。
4. 分析流程與資料分流：說明 DistilBERT、LLM 與程式驗證各自負責的工作。
5. 結果邊界：能判斷、不能判斷，以及下一步需要的資料。
